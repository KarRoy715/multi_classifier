# 实验计划与决策记录

本文记录**为什么这么设计**，以及每一步的**判定标准**。README 讲怎么用，本文讲为什么。

---

## 1. 目标与范围

把 ICT 图片分到 15 个细类。数据在 `multi_data/data0910/rejudged/`，一层子目录名即类别名。

**范围界定（已确认）**：

| 决定 | 说明 |
|---|---|
| **不做相关性门控** | `不相关` 从数据划分开始就排除，当作不存在。曾考虑「先二分类过滤不相关」的两阶段方案，**已否决** |
| **不做拒识** | `predict.py` 对所有输入都给 15 选 1 的答案 + 置信度，是否采信由使用方决定 |
| **全保留 15 类** | 稀有类不合并、不删除，但标记 `unreliable`，指标不进主口径 |
| **先比 backbone 再微调** | 特征缓存 + 线性探针的成本几乎为零，先花小钱把底座选对 |
| **参数走 YAML** | 不用 CLI 传参，便于记录与复现每一次实验 |
| **交付脚本 + README** | 训练由使用者自己的服务器执行，所有绝对路径可配置 |

## 2. 数据勘察结论（全部实测，非推测）

| 项 | 实测值 |
|---|---|
| 图片总数（排除`不相关`后） | **11,529 张 / 15 类** |
| 不可读 / 损坏 | **0 张** |
| md5 层面重复 | **0 对** |
| dHash 层面完全相同 | **48 对**（同图不同压缩/编码） |
| 汉明距离 ≤4 的近重复对 | 约 1,900 对（平均每张 0.21 个近邻） |
| **横跨两个不同标签的近重复组** | **87 个** ← 直接的标签噪声证据 |
| 不均衡比 | `电路与工程设计图 : 质量类` = 3701 : 8 ≈ **463 : 1** |
| 长宽比 ≥ 2 的占比 | 31.4% |
| letterbox 缩到 336 后最短边 | min=16.7px，中位数 213px，**无一张塌缩** |

**两个已确认的坑**：
1. `器件资料` 命名不一致——原始目录 `器件资料类`，复核输出写 `器件资料`。类名统一在 `configs/classes.yaml`，用别名映射处理，杜绝类名漂移导致标签整体错位。
2. `质量类` 的 10 张几乎全由别的类改判而来，类内一致性无保证 → 标 `unreliable`。

**判别信号的性质**：内容形态是混合的（工程图纸、CAD 截图、论文插图、设备实拍、灰度检测图、认证文档），
但判别依据主要是**图里的文字标签与排版**，不是自然图像纹理。这一条推出了下面两个预处理决策。

## 3. 三个关键决策

### 3.1 letterbox，而不是 resize + centercrop

裁剪会切掉长图两端的文字，而文字正是判别信号。本库 31.4% 的图长宽比 ≥2，损失会很明显。
letterbox 等比缩放 + 白边补齐，完整保留整图；且多数图表本身就是白底，白边能自然融合。

**已实测安全性**：缩到 336 后最短边中位数 213px、最小 16.7px，没有任何一张被压塌（<32px 仅 35 张）。

### 3.2 温和增强，不做水平翻转 / 大裁剪

翻转会破坏文字方向，大裁剪会切掉内容——两者都会破坏真正的判别信号。
只做小幅尺变/平移/旋转（±2°、±3%）+ 轻微颜色抖动。验证集始终用原图，保证 epoch 间指标干净可比。

### 3.3 指标双口径，选模型用「可靠类 macro-F1」

`质量类` 在 val 上只有 **2 张**，其 F1 只能取 0 / 0.5 / 1.0 三者之一，单张翻转就能让 15 类 macro-F1
抖动 ±0.03 以上。把它算进主指标，等于让噪声主导结论。

因此所有评估同时报：
- `macro-F1 (15 类全量)` —— 与外部口径对齐
- **`macro-F1 (仅 10 个可靠类)`** —— **判断模型好坏、选模型、早停都用这个**

同理，`top_confusions` 按「占真实类样本的比例」排序而非绝对计数，避免 4626 张的大类霸榜。

### 3.4 继承兄弟项目的三条硬结论

兄弟项目 `image_classifier` 在同源 ICT 数据上做过二分类（val macro-F1 ≈ 0.93），留下：

| 结论 | 证据 | 本项目的对应默认值 |
|---|---|---|
| **过拟合而非欠拟合** | train recall 冲到 0.97，val 卡在 0.93 | `weight_decay 1e-3`（而非 1e-4）、`augment mild`、`unfreeze_blocks 2`（而非 4）、`label_smoothing 0.1` |
| **分辨率不是杠杆** | 448 ≈ 336 | 用 backbone 原生分辨率 |
| **标签噪声才是天花板** | 评估口径必须诚实 | 双口径 macro-F1；专门报告最易混类对指导补数据 |

> **调参方向提醒**：过拟合对应的杠杆是**更强的正则**（更高 weight_decay、更少解冻层、更强增强），
> **不是更高的学习率**。这是最容易走反的一步。

## 4. 实验路线与判定标准

```
阶段 0  数据划分        prepare_data.py
   ↓   判定：0 泄漏（断言）、不相关已排除、15 类齐全
阶段 1  特征缓存        extract_features.py
   ↓   判定：行数 == 11529、维度与 feat_dim 一致、同一图两次抽取余弦相似度 > 0.999
阶段 2  backbone 大比拼  linear_probe.py          ← 第一步正式实验
   ↓   判定：显著高于随机 1/15 ≈ 0.067；选出胜者
阶段 3  微调            train.py
   ↓   判定：val macro-F1(可靠类) > 阶段 2 的线性探针（否则说明微调没带来增益）
阶段 4  评估与推理      evaluate.py / predict.py
       判定：确认双口径指标都在、unreliable 已标注、混淆矩阵可读
```

**阶段 2 是关键的成本控制点**：特征缓存一次（约 1–2 小时），之后换模型结构、换超参重训 head
都不用再碰 backbone。探针训练是秒级的，因此「哪个 backbone 适合本任务」这个问题几乎零成本回答。

**阶段 3 的对照基线是阶段 2 而非 0.067**：如果微调后的指标还不如冻结特征的线性探针，
说明微调过程出了问题（通常是 lr 太大或解冻过多）。

### 5.4 全链路冒烟测试

> ⚠️ **下面的数字来自 771 张的分层子集（每类 40 train / 15 val），只为验证脚本能跑通，
> 不是真实性能结论。**真实数字需在全量数据上跑。

用分层子集跑通 `extract_features → linear_probe → train → evaluate → predict` 全链路：

| 探针 | clip_l336 | dinov3_l16 | siglip2_b32 |
|---|---:|---:|---:|
| logreg (可靠类 macro-F1) | 0.546 | 0.516 | 0.468 |
| mlp | 0.479 | 0.449 | 0.391 |
| knn | 0.399 | 0.378 | 0.356 |

**这些数字的意义**：全部显著高于随机水平 1/15 ≈ 0.067，说明**标签与划分是可信的、流程是通的**。
样本量太小（每类 40 张）且只训了 2 epoch，所以模型间差距不足以作为选型依据——
**真正的选型要在全量数据上跑阶段 2**。

冒烟测试同时验证了：`train.py` 存出的 `best.pt` 含完整的复现元信息
（`model_name_or_path` / `resolution=336` / `preprocess=letterbox` / `class_names` 15 类）、
`evaluate.py` 的中文混淆矩阵 PNG 正常渲染、`predict.py` 单图与目录批量两种模式都正确。

### 5.5 已知会重现的现象

在 771 张子集上，`文档与认证图片 → 电路与工程设计图` 的错误率达 40%，
`仿真分析图片 → 信号与波形图片` 达 33%。这与复核期记录的易混方向一致
（`电路与工程设计图 → 产品与结构图片` 1313 次、`→ 文档与认证图片` 675 次、
`电子元器件图片 → 文档与认证图片` 192 次）。**这些类对的标注边界值得人工复核。**

## 6. 待定问题（需要人工决策）

1. **`unreliable` 类怎么处理**——保留（现状）会把 15 类 macro-F1 拖得很难看且无实际意义；
   合并进相近类或删除会让指标更干净。取决于业务上是否真的需要区分这 5 类。
2. **`质量类` 是否值得保留**——仅 10 张，且几乎全是改判而来。若业务需要，应重新标注扩样。
3. **87 个跨类近重复组**是标签噪声的直接证据，建议人工过一遍这些组，确认正确标签。
4. **`unfreeze_blocks` 的最优值**——当前默认 2 是继承兄弟项目并下调的保守值。
   若 val 迟迟不涨且 train 也没拟合上去，可试 4/6；若 train 明显高于 val，则维持 2 或降到 1。

## 7. 复现性保障

- 每个阶段的输出目录都写 `resolved_config.yaml`：深合并后的完整配置 + git commit + python 版本 + 平台。
  **每个实验目录自解释**，回头不用猜当时跑了什么。
- 多 YAML 深合并：`base.yaml` 是全局默认，`configs/exp/*.yaml` 只写差异。
- 随机种子全程固定（`runtime.seed` / `train.seed` / `data.seed`），近重复分组结果可复现。
- `extract_features.py` 的缓存带 `meta.json` 记录维度/分辨率/预处理，换配置后维度不符会直接报错而非静默复用。
